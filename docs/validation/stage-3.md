## 수정 내용

- 기물 가치를 `PieceType` 이름으로 조회합니다. 이전 배열은 존재하지 않는 None 슬롯으로 시작해 폰=0, 비숍=100, 룩=330, 퀸=500, 킹=900으로 잘못 조회됐습니다. 폰 100, 나이트 320, 비숍 330, 룩 500, 퀸 900, 킹 100,000을 평가와 두 수 정렬 함수에 동일하게 적용합니다.
- PST의 행은 백 기준 1랭크부터 8랭크입니다. 보드의 row 0은 8랭크이므로 백은 `7-row`, 흑은 `row`로 조회합니다. 백 a2 폰=5, a7 폰=50, g1 킹=30과 색/랭크를 뒤집은 흑 대응 칸을 테스트합니다.
- 통과폰 검사는 백의 앞쪽을 행 감소, 흑의 앞쪽을 행 증가로 검사합니다. 승급에 가까워질수록 통과폰 보너스가 커집니다. 폰 뒤에 있는 상대 폰 때문에 통과폰을 부정하던 문제도 수정했습니다.
- 정상 탐색과 Quiescence는 깊이 제한·stand-pat 컷오프보다 먼저 메이트, 스테일메이트, 기존 `Board.InsufficientMaterial`을 확인합니다. 무승부 점수는 0입니다. 메이트 점수에는 루트부터의 반수 거리를 반영하여 빠른 승리/늦은 패배를 선호합니다.
- Quiescence에서 체크 중에는 stand-pat을 사용하지 않고 모든 합법 회피 수를 탐색합니다. 체크가 아닐 때만 잡기·앙파상·승급으로 후보를 제한합니다. Q 깊이를 소진한 체크 국면은 한 번의 합법 회피를 추가로 적용하고, 자식의 종료 판정 후 정적 평가합니다. 이 경계 정책은 반복 체크에 의한 무제한 재귀를 막기 위한 유한 근사입니다.
- 루트·정상 탐색·Quiescence의 후속 보드는 `NextBoard`에서 `Board.Copy`와 2단계 `GameState.MakeMoveForTraining`을 사용합니다. 새 2칸 전진 표시는 남고, 응수한 앙파상 기회는 만료됩니다. 입력 보드와 기물 이동 플래그는 변경하지 않습니다.

코드 변경은 `Assets/Scripts/Engine/SimpleChessEngine.cs`와 PST 좌표 설명 주석에 한정합니다. `IChessEngine` 인터페이스, 게임 진행/UI, 학습 에이전트, 평가 테이블의 숫자는 변경하지 않았습니다. 기존 정적 평가의 가중치 조정이나 강도 튜닝은 이번 목표가 아닙니다.

## 테스트 근거

`Assets/Tests/EditMode/Editor/Stage3EngineTests.cs`는 직접 배치한 국면, 명시적인 점수 기대값, 색과 랭크를 뒤집은 대칭 국면을 사용합니다. private 함수는 테스트 내부 reflection으로 확인하며 생산 API를 테스트 편의상 공개하지 않습니다.

- 모든 기물의 정확한 가치와 색에 따른 부호, PST의 구체적인 칸 점수, 통과폰 방향/진행 보너스, 초기 배치 0점과 색 대칭성.
- 일반/전술 수 정렬의 퀸 잡기와 앙파상 점수, 네 승급 선택의 가치 순서.
- 양쪽 색의 메이트·스테일메이트를 탐색 깊이 -1/0/1과 좁은 알파·베타 창에서 확인. 기물 부족도 정상 탐색과 Quiescence 양쪽에서 확인.
- 유일한 수가 조용한 킹 이동 또는 룩 가로막기인 체크 국면. Q 깊이 0에서도 실제 회피 후 평가하는지 확인. 킹 이동 사례는 상대의 전술적 응수가 없음을 별도로 검증하여 한 수 뒤 평가를 기대값으로 삼습니다.
- 손해 보는 잡기 후 재잡기, 잡기 없는 승급, 앙파상이 Quiescence에 포함되는지 확인.
- 양쪽 색의 한 수 메이트와 공짜 퀸 잡기를 실제 `GetBestMove` 호출로 검증. 수정 전에는 흑의 한 수 메이트 국면에서 스테일메이트를 선택했습니다.
- 엔진 호출 후 입력 보드의 문자열뿐 아니라 기물 객체 참조와 이동 플래그의 보존을 확인합니다.

기존 68개에는 2단계의 네 perft 국면과 실제 MainScene 진행 통합 테스트가 포함됩니다. 따라서 규칙/특수 행마/승급 콜백/AI 예약 취소/일시정지 흐름의 기존 검증도 함께 통과했습니다.

## 재현과 로컬 산출물

테스트는 검증 작업 트리의 프로젝트 루트에서 실행했습니다. Unity 실행 경로는 아래와 같습니다. 샌드박스의 라이선스 제약은 이전 단계에서 확인되어, 정식 권한 상승으로 사용자 환경에서 실행했습니다.

```powershell
New-Item -ItemType Directory -Force Validation/Stage3 | Out-Null
& 'C:\Program Files\Unity\Hub\Editor\6000.0.30f1\Editor\Unity.exe' -batchmode -nographics -runTests -testPlatform EditMode -testResults "$PWD\Validation\Stage3\after.xml" -logFile "$PWD\Validation\Stage3\after.log" -projectPath "$PWD"
```

수정 전 실행은 `-testFilter Stage3EngineTests`를 추가했으며 `before.xml`, `before.log`에 저장했습니다. 전체 테스트의 최종 결과는 `after.xml`, `after.log`입니다. 테스트용 Unity가 완전히 종료된 것을 확인한 뒤 기존 빌드 도구를 실행합니다.

```powershell
& 'C:\Program Files\Unity\Hub\Editor\6000.0.30f1\Editor\Unity.exe' -batchmode -nographics -executeMethod Stage0ValidationBuild.Run -logFile "$PWD\Validation\Stage3\build.log" -projectPath "$PWD"
```

기존 도구는 실행 파일을 `Validation/Stage0/Windows64/Chess.exe`, 빌드 요약을 `Validation/Stage0/build-summary.txt`로 출력합니다. 따라서 이 고정 경로의 2단계 빌드 산출물은 이번 빌드로 갱신됩니다. 단계별 테스트 XML/로그는 별도 폴더에 보존됩니다. `Validation/`은 Git에 포함하지 않습니다.

Unity 실행 도중 변하는 설정을 확인했고, 종료 후에는 `11d8654b` 대비 렌더링 asset과 `ProjectSettings`의 의미 있는 내용 차이가 없었습니다. 2단계에 커밋된 자동 생성 설정은 보존합니다. 이번 인계 대상은 엔진 두 파일, 신규 테스트와 `.meta`, 이 문서의 다섯 파일이며 원본 `dev_game`에 반영합니다. 커밋·푸시는 이번 요청에 포함하지 않았습니다.

## 제한과 다음 단계

Quiescence 깊이 8 및 경계에서 한 번의 체크 회피라는 유한 탐색이므로, 더 긴 강제 전술을 모두 해결한다는 의미는 아닙니다. 경계의 회피 수가 다시 체크를 걸면 그 자식은 종료 여부까지만 판정한 뒤 정적으로 근사합니다. 장시간 대국, Elo/성능 비교, 빌드의 수동 화면 QA는 수행하지 않았습니다.

`IChessEngine`은 `Board`와 차례만 받으므로 실제 대국의 반복 이력/반수 카운터를 전달받지 못합니다. 따라서 탐색 내부의 3회 반복·50수 무승부 평가는 이번에 추가하지 않았고, 실제 게임의 해당 판정은 기존 `GameState`가 담당합니다. 기물 부족 판정은 기존 구현 범위(킹 대 킹, 단독 비숍/나이트 대 킹, 같은 색 칸 비숍 대 비숍)를 따릅니다.

다음 로드맵은 4단계 구조/assembly 개선입니다. 시간 제한·비동기화·UI 반응성 및 탐색 성능은 5단계에 남깁니다.
